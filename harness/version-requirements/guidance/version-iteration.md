# 版本迭代与维护线

[共同约束](README.md) · [接收新包](s0-intake.md) · [同版本需求变更](requirement-change.md)

本页用于新产品版本的受理、需求继承及目标线交付。新版本重新执行 S0～S4，建立自己的来源、scope、验证责任和 BL；可复用仍适用的历史内容与审查依据。工具不自动复制旧版本、裁决产品差异或执行移植。

## 1. 固定起点并接收新输入

在业务仓库的独立工作区核对实际目标分支、HEAD、未提交工作和当前控制提交。准备新 PRD 包或产品明确提供的增量包、前序最终获批 BL 及发布观察，以及目标线当前代码、主 Spec、配置和资源。后续可用的完成/发布候选也应明确选择；当前已有 BL 或单 Change 的 PASS 不能冒充整版完成。

建立 `requirements/versions/<新版>/version.yaml`，填写真实 `delivery_line`、`integration_ref`、`starting_commit`、负责人及 `predecessor_version / predecessor_baseline`。核对选定前序时已经批准并实际交付的状态，纳入此前的需求变更，而非只按初始 PRD 文件名取版本。首次采用需求层的旧系统若没有 BL，应先明确已有能力的采用范围，不伪造历史基线。

新版受理后，旧线仍可能继续变更；已选前驱保持固定，不自动跟随旧线的新 BL。比较两线承诺和实际实现，记录需要同步、不适用或已具备的依据。需要同步的需求变化在新版首 BL 前复核受影响的 S0～S3，首 BL 后沿本版 RC 处理；工程移植按第 4 节使用目标线证据。不能通过移动前驱引用隐式接受变化，或用旧线 PASS 代替新版验证。

按 [S0](s0-intake.md)接收 full/delta，保存原目录和字节。跨版本 delta 的 `predecessor` 固定指向所选旧 BL 内容提交中的 `source/manifest.yaml`；旧 DOC/AST/SRC 保持原所有者，新版只登记新增接收单元。读取旧包、配置和附件的全部固定对象，不能依赖另一个工作区的缓存。缺少前序或产品未明确按增量交付时，停止依赖它的受理，不猜测缺失正文。

发给已获上游受理授权的 Agent：

```text
从实际新 PRD 包、选定前序 BL 及目标线工程状态执行本版 S0～S4。
先核对来源所有者和完整留存；逐项列出新来源及旧承诺的采用决定。
复用未变 R 的确切字节，保留原 AC ID；新语义按当前线修订。
未知、遗漏和冲突记录到 Q，不自动判为删除或继承。
为全部纳入 AC 建立交付和验证责任，报告各阶段检查及真实批准缺口。
本次上游授权不包括候选释放、Propose、Apply 或发布。
```

## 2. 对账旧承诺与新来源

S1 对新版目标、旧功能处置和实际适用的共享约束执行 Challenge；S2 按真实差异建模。下面的分类由产品/工程判断形成，文本 diff 不能直接授予它们。

| 判断 | 当前资料如何保存 | 后续责任 |
| --- | --- | --- |
| 新业务承诺 | scope `transition: added`，分配新 R ID 和来源映射 | S3 分配真实交付路径与全部 AC 验证 |
| 同一承诺的语义变化 | 保留 R ID，推进本线 revision，scope `modified` 固定原前驱 | 重新审阅受影响来源、AC、依赖及工程规划 |
| 原样继承 | scope `inherited` 固定原 BL、R 和原配置；新来源的确认写 `source_confirmations` | 不修改旧 R 的起源，仍检查目标线能力和本版验证责任 |
| 明确删除或延期 | scope `excluded` 保存 `removed / deferred`、确切前驱及已落实/复核的决定 Q | 原记录不删除；撤下已接受行为还须有明确退役义务和实际处置 |
| 未知、遗漏或冲突 | 保留开放 Q 和受影响集合 | 阻断依赖决定的基线，不默认沿用或排除 |

本版首 BL 必须对账所选前序 scope 的全部纳入义务。未出现在新稿的旧功能也需要明确纳入或排除；旧的一次性迁移等义务则按本版是否适用裁决。产品可以明确确认一组未变能力，scope 逐项记录同一决定依据，无需重写相同正文。

后续本版 RC 的对账前驱是本版当前有效 BL；首次迭代时已经批准退出的旧版义务不因再次保存 BL 而重新出现。旧退出决定仍保留在历史 BL 中，不能删除历史对象来省略对账。重新纳入历史承诺时先核对业务身份和差异，再选择 inherited/modified，不能重复分配成无关新 R。

## 3. 建立本版独立基线

按 [S3](s3-engineering.md)读取目标线真实代码、主 Spec 与构建/资源事实，检查全量贡献、依赖、共享约束和验证计划。`inherited` 表示业务语义未变，`already-satisfied` 表示工程交付路径；前者可能仍需要移植，后者仍需要本线适用证据。

按 [S4](s4-baseline.md)分别运行 G1/content、record、effective。新版本首 BL 的 `supersedes` 为 null；跨版本关系保存在 version/scope，不能让新 BL 取代旧版链头。Review 和真实三方批准绑定本版确切 C，历史批准仅沿其真实适用范围复用。快照的 `baseline_contexts` 包含被读取的各个历史 BL 的原发布语境和当前查询事实。

保持业务历史、当前查询和新元数据分开：所有线都从同一权威控制分支读取最新事件；按 S4 的固定对象留存合同发布新 C/B、Review、执行证据等实际输入所需的 pins。留存集合取自实际输入闭包，不能只遍历名为 `main` 的分支。失败先核对固定引用、实际远端和已完成步骤，再恢复原记录；不重建 ID 或改写已发布 BL。

## 4. 在目标线实施与验证

新版基线生效后，候选按 [S5](s5-dispatch.md)滚动释放。工程规划使用目标线当前事实，不批量复制旧 Change 的 Design/Tasks。

- 目标已具备的能力，按 [S6 scope 路径](s6-delivery.md#无-change-的交付核对)核对本版 R/AC 和当前证据，不造空 Change。
- 需要演进或移植的能力，根据本线语义、真实 diff 和已有工程状态选择 Tiny/Standard。Standard 新建本次目标线 Change，以旧归档作为背景引用；已有未合并的同轮 Standard 工作仍沿原恢复入口。
- Tiny 使用真实任务/PR 和本线请求，沿 [S6 Tiny 路径](s6-delivery.md#tiny-任务pr-的交付核对)完成回归、实际合并和当前 G3。移植记录源修订、目标起点与实际补丁/提交；复制代码不复制源端 PASS。
- 同一 `R-001@2` 在两条线可以有不同内容。Record、配置、BL、Assets 和 E 都按完整固定引用选择，不能只比较 ID/revision 或文件名。新 E 使用目标线的 tested_revision、运行输入、原始报告和具名 Review。

一条线可以承载多个产品版本，容量按原交付线控制协议共享；不同线的容量和暂停范围按明确配置核对。R ID 仍由同一项目整合者或已发布编号段协调，跨线 inherited/modified 不重新分配旧身份，新承诺不能占用别人的编号。

## 5. 失败恢复与交接

| 失败 | 下一步 |
| --- | --- |
| 新包缺前序、原 manifest 不属于所选 BL、来源所有者错误 | 核对选定前序和固定对象；修正当前引用，保留原包 |
| 前序义务遗漏、决定未落实或来源映射冲突 | 回 S1/S2 取得决定并实际落实，再重绑受影响 Review |
| 另一线已经 PASS，但本线缺实现或证据 | 保留原结果；在目标线实施或运行实际适用检查 |
| 缺留存 pin、目标/控制快照已过时 | 先查询实际远端并补所需留存/当前快照；不放宽 Gate 或重复占额 |
| 移植冲突、规格变化或验证失败 | 保存实际停点，沿所选工程路径处理；不强行合入整个源版本 |

交接新版 C/B、历史 BL/来源引用、分类与开放 Q、实际目标线、当前控制、候选及本线 E。停止维护或旧版完成不授权删除其他版本仍引用的 R、配置、原包、派生物和归档。当前版本迭代与交付检查限隔离试用；最终通过 [S7](s7-completion.md)核对各自的整版组合，不能用两条线的单项绿色结果代替版本验收。
